# Open-Meteo Weather Integration Design

Date: 2026-06-14

## Goal

Replace the homepage's simulated weather values with real forecast data from
Open-Meteo while keeping the first version small and stable.

The feature covers:

- Fetch current and hourly weather for the selected mountain.
- Display real temperature, humidity, wind speed, and weather status on the
  existing homepage.
- Keep route guide content as static local data for now.
- Compute cloud-sea probability locally from real weather fields.
- Cache weather responses locally to reduce repeated API calls.

## Current State

The mini program currently registers only `pages/index/index` in `app.json`.
The homepage data is defined in `pages/index/index.js`:

- Mountain information and route guide content are hardcoded in a local
  `mountains` array.
- Three forecast cards are generated by `buildForecasts`.
- Weather values are simulated from dates and each mountain's `baseProbability`.
- No real weather API or database is used.

## Recommended Approach

Use frontend direct access to Open-Meteo with local storage caching.

Open-Meteo's Forecast API supports requests to
`https://api.open-meteo.com/v1/forecast` with latitude, longitude, `current`,
and `hourly` parameters. It does not require an API key for the intended first
version. The mini program must add `https://api.open-meteo.com` as a legal
request domain before production preview or release, because
`project.config.json` has `urlCheck` enabled.

This approach is preferred for the first version because:

- Mountain count is small and static.
- Weather data is real-time forecast data, so persistent database storage is
  not required.
- Open-Meteo does not require a secret key that must be hidden server-side.
- It avoids cloud function and database setup before the product needs them.
- It keeps failure behavior simple: use cached data or fall back to existing
  local simulated values.

## Out Of Scope

This first version will not add:

- A database for mountain guides.
- Weather history storage.
- A cloud function proxy.
- Admin editing for mountain content.
- User accounts, favorites, comments, or personalized records.

These can be added later when route content needs editing, users need saved
data, or API call volume requires server-side caching.

## Data Model

Each mountain should include coordinates:

```js
{
  name: '黄山',
  slug: 'huangshan',
  province: '安徽',
  city: '黄山市',
  latitude: 30.132,
  longitude: 118.166,
  // existing route and display fields
}
```

Coordinates are used only for weather lookup. Existing display fields such as
`sunrise`, `window`, `routes`, and `altitude` stay local.

The `slug` field is an ASCII-safe identifier used as part of the cache key.
It must be unique across all mountains in the `mountains` array.

Weather service output should be normalized for the page:

```js
{
  updatedAt: 1718340000000,
  current: {
    temperature: 18.4,
    humidity: 92,
    windSpeed: 2.8,
    weatherCode: 3,
    weatherLabel: '多云',
    weatherIcon: '☁'
  },
  dailyForecasts: [
    {
      offset: 0,
      temperature: 18,
      humidity: 90,
      windSpeed: 3.1,
      weatherCode: 3,
      weatherLabel: '多云',
      weatherIcon: '☁'
    }
  ]
}
```

## API Request

The weather service will call:

```text
https://api.open-meteo.com/v1/forecast
  ?latitude=<mountain.latitude>
  &longitude=<mountain.longitude>
  &current=temperature_2m,relative_humidity_2m,wind_speed_10m,weather_code
  &hourly=temperature_2m,relative_humidity_2m,wind_speed_10m,weather_code
  &forecast_days=3
  &timezone=auto
```

`timezone=auto` instructs Open-Meteo to return timestamps in the local time
zone for the requested coordinates. All `hourly.time` values are local
ISO-8601 strings (e.g. `"2026-06-14T08:00"`). When parsing or comparing these
times, treat them as local time, not UTC.

The response is transformed into the existing homepage fields. Each entry in
`dailyForecasts` is derived from the `hourly` arrays, not from a separate
`daily` parameter. For each day, aggregate the hourly records as follows:

- **temperature**: the value at the hour closest to the mountain's observation
  window, or the daytime maximum if no window is defined.
- **humidity** and **windSpeed**: average of all records between 06:00–18:00
  local time for that day.
- **weatherCode**: the modal (most frequent) code among 06:00–18:00 records.

If the exact hour is unavailable, fall back to the nearest available daytime
or current record.

## Data Flow

1. User opens the homepage.
2. `pages/index/index.js` selects the current mountain.
3. The page calls `services/weather/index.js` with mountain coordinates and
   selected date.
4. The service calls `wx.getStorageSync` to check for a fresh cached response.
   This is a synchronous call on the main thread; it is acceptable here because
   local storage reads are fast, but the key must be kept short (use the
   slug-based key, not the raw mountain name) to avoid unexpected encoding
   overhead from non-ASCII characters.
5. If cache is fresh, the page uses it immediately.
6. If cache is missing or stale, the service calls Open-Meteo with `wx.request`.
7. The service normalizes the response.
8. The page builds forecast cards, factor rows, and cloud-sea probability from
   normalized data.
9. If API access fails, the page shows a lightweight toast and falls back to
   the current simulated values.

## Cache Strategy

Use local mini program storage keyed by mountain slug and selected date:

```text
weather:<mountain-slug>:<yyyy-mm-dd>
```

Cache duration: 30 minutes.

This is enough for the first version because weather data changes during the
day but does not need second-level freshness. It also reduces API calls when
the user switches between routes or revisits the same mountain quickly.

## Cloud-Sea Probability

The probability should remain a local heuristic. The first version can combine:

- Higher humidity increases probability.
- Lower to moderate wind speed increases probability.
- Weather codes for cloudy, foggy, rainy, or overcast conditions increase
  probability.
- Very strong wind or dry air reduces probability.
- Each mountain's existing `baseProbability` remains a local baseline.

The exact formula should be simple and bounded from 20 to 96. It should be
isolated in a helper function so it can later be replaced by a better model.

## UI Behavior

The existing layout should remain mostly unchanged:

- Forecast cards show real temperature, humidity, wind speed, weather label,
  and probability.
- The probability card uses real humidity, wind speed, and temperature.
- The selected mountain panel's weather text should be rebuilt from real
  current weather.
- Loading state should be subtle. The page can show existing values while
  refreshing, then update after the request finishes.
- On request failure, show `wx.showToast({ title: '天气数据暂不可用', icon: 'none' })`
  once per failed refresh.

## Error Handling

The weather service should handle:

- Missing coordinates.
- Network failure.
- Non-200 HTTP status.
- Missing `current` or `hourly` fields.
- Empty hourly arrays.

Failure should not blank the homepage. The existing simulated forecast
generation remains a fallback path.

## Testing

Add focused tests for pure logic where practical:

- Open-Meteo response normalization.
- Weather code to display label/icon mapping.
- Cloud-sea probability bounds and major factors.
- Cache freshness decision.
- Cache key generation: verify that slug-based keys for all mountains produce
  consistent, ASCII-safe strings with no collisions.
- Cache expiry boundary: a response stored exactly 30 minutes ago is treated
  as stale; a response stored 29 minutes ago is still treated as fresh.

Manual verification in WeChat DevTools should cover:

- Homepage loads with a selected mountain.
- Switching mountain refreshes weather.
- Changing date refreshes or reuses cache correctly.
- Network failure does not break the page.
- The request domain requirement is documented for release.

## Database Decision

Do not add a database in this version.

A database becomes useful when at least one of these requirements appears:

- Mountain guide content needs admin editing.
- Users can save favorite mountains or trips.
- Weather history needs to be queried or charted.
- API call volume becomes high enough that server-side caching is required.
- The project needs audited, versioned route content.

Until then, local mountain guide data plus real-time weather API access is
simpler and easier to maintain.
